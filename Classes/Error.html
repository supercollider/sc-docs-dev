      Error : Exception : Object : AbstractObjectExperimental

      superclass of all Errors
      Source: Error.sc
      Subclasses: ErrorWrapper, MethodError

      Description

      Error and its subclasses separate different types of error is that can occur in the SuperCollider program into distinct classes, so that they can be reported differently to the user.

      Anywhere that an error must be reported to the user and execution must stop, an error object must be created and thrown.

      For backward compatibility, .die() creates the error for you.

      Throwing an error object gives the caller the opportunity to catch, and possibly recover from, the error. See the Exception help file for more information about this.

      Error hierarchy

      The following error classes exist in the main library.

      • Error
      • ErrorWrapper : wraps an existing error in another.
      • DeprecatedError : this method is no longer supported.
      • MethodError : generic error occurring within a method.
      • DoesNotUnderstandError : the receiver does not understand the method name.
      • BinaryOpFailureError : a binary operator cannot work with the operand classes.
      • ImmutableError : attempted to modify an immutable object.
      • MustBeBooleanError : a test (in if or while) returned a non-Boolean value.
      • NotYetImplementedError : the method name exists, but isn't implemented yet.
      • OutOfContextReturnError : a method return by ^ took place outside of a method.
      • PrimitiveFailedError : an error occurred inside a primitive.
      • ShouldNotImplementError : you called a method on a class that has no business implementing it.
      • SubclassResponsibilityError : you called a method on an abstract class.

      The exact inheritance tree looks like this:

      • Error - superclass of all Errors
        • ErrorWrapper - Error used to wrap another error
        • MethodError - (Undocumented class)
          • DeprecatedError - (Undocumented class)
          • DoesNotUnderstandError - Error thrown when calling an unknown method name
            • BinaryOpFailureError - (Undocumented class)
          • ImmutableError - (Undocumented class)
          • MustBeBooleanError - (Undocumented class)
          • NotYetImplementedError - (Undocumented class)
          • OutOfContextReturnError - (Undocumented class)
          • PrimitiveFailedError - (Undocumented class)
          • ShouldNotImplementError - (Undocumented class)
          • SubclassResponsibilityError - (Undocumented class)

      Changing how a custom error is displayed

      The only reason you should ever need to write an new type of error is if you intend to catch it and do some custom recovery logic with it. Otherwise, you just should use Error

      There are two places you can change how an error is displayed, when it is constructed, and through overloading two specific methods.

      If you only need to change the constructor arguments, consider using Error directly.

      The constructor of Error takes 4 arguments.

      First, a string saying what went wrong, this should describe the type of error.

      Second, callFrameAnnotations, this is an array of nil or strings. Working up the call stack, the text is shown next to the source code. This is best shown by example.

      This produced an error report like this... remember, in the post window, this is read bottom to top!

      Third, methodBeforeBacktraceStart this is a function that returns true when encountering a method in the call trace which we would like to start printing after. The simplest example is skipping everything before the throw method of the exception (the default), but it the case of DoesNotUnderstandError it is also used to skip Object:doesNotUnderstand too.

      Fourth, MethodBacktraceEnd this is a function that return true when encountering the method one past the final backtrace we would like to print. The default here will stop printing when we get to a try, protect, or go up into the interpreter methods.

      When it comes to overriding methods, the two (and only two) that are allowed are reportStage1 and reportStage2. These are responsible for printing the backtrace and adding any additional information. If you only want to add additionally information at the end of the report, you can just overload reportStage2. See the definition below for more information on these.

      Class Methods

      Error.new(what: "", callFrameAnnotations: [], methodBeforeBacktraceStart, methodBacktraceEnd)

      From superclass: Exception

      Arguments:

      what

      A String describing the error. In some cases a subclass may alter this, appending information as needed.

      callFrameAnnotations

      An Array containing either a Nil or a String. Working up the call stack, the text (if present) is printing next to the source code. See the example above for an example.

      methodBeforeBacktraceStart

      A Function that accepts a FunctionDef that returns a Boolean. Internally, we walk up the call frame, if this function returns true, it means we will skip all the previous frames and this one, starting the trace on the next method. This is often used to skip the creating and throwing of the error, and sometimes a helper function that is used to create it.

      methodBacktraceEnd

      A Function that accepts a FunctionDef that returns a Boolean. When walking up the call frame, if this returns true, we stop printing the backtrace. This is often used to skip printing above a try block and to stop printing the internal interpreter details.

      Instance Methods

      .throw

      From superclass: Exception

      Throw the error, creating a backtrace. This will not override the previous, if you would like to store where you rethrow the error or add additional information, see ErrorWrapper.

      .reportStage1(stream, prefix)

      From superclass: Exception

      This is used to print the backtrace, there is little reason to override this.

      Arguments:

      stream

      The stream we are writing to

      prefix

      The prefix that must be inserted after each new line.

      .reportStage2(stream, prefix)

      From superclass: Exception

      This is used to print any custom message an exception might have. If you want to add some information to your own error, this is where you place it.

      Arguments:

      stream

      The stream we are writing to

      prefix

      The prefix that must be inserted after each new line.

      .reportError(stream, prefix: "")

      From superclass: Exception
      WARNING: Do not override this! Instead see reportStage1 and reportStage2.

      Arguments:

      stream

      The stream to write to, by default this is Post

      prefix

      The prefix that must be inserted after each new line.

      .errorString

      From superclass: Exception

      This returns the what of the error. See ErrorWrapper.

      .path

      .path = value

      From superclass: Exception

      Returns the result of thisProcess.nowExecutingPath as evaluated when the exception was created. Looking at the backtrace is a more reliable way to see where the exception was thrown from.

      .backtrace

      From superclass: Exception

      Returns the underlying backtrace created when the exception was thrown. Returns nil if it was never thrown.
